## 2. 地点解析设计

### 2.1 地点对象，而非字符串替换

601 查询依赖稳定 `place_id`，显示名称只是属性。最小对象：

```json
{
  "place_id": "PLACE-CN-120116",
  "official_name": "滨海新区",
  "place_type": "county_level_admin",
  "admin_code": "120116",
  "parent_place_ids": ["PLACE-CN-120100", "PLACE-CN-120000"],
  "valid_from": null,
  "valid_to": null,
  "source_id": "SRC-OFFICIAL-PLACE-...",
  "locator": "行政区划表/天津市/滨海新区"
}
```

开发区、新区、片区不能假装成法定区县。用 `place_relation` 表达：

- `admin_parent`：法定行政隶属；
- `managed_by`：管理关系；
- `overlaps`：跨一个或多个行政区；
- `located_within`：完全位于某行政区；
- `historical_alias_of`：旧称；
- `informal_alias_of`：俗称或项目常用名。

关系必须有 `valid_from / valid_to / source_id / locator / review_status`。没有官方证据时只能作为待核实候选。

### 2.2 别名分类

| alias_kind | 示例用途 | 自动采用 |
|---|---|---|
| `official_short_name` | 省略“省/市/区” | 仅在父级上下文唯一时可进入“可确认” |
| `historical_name` | 撤县设区、旧行政名 | 必须按项目日期核对 |
| `development_zone_name` | 开发区、功能区、产业园 | 不自动折叠为区县 |
| `local_usage` | 当地俗称 | 只召回，不自动采用 |
| `project_declared` | 项目资料中的地点写法 | 需与官方行政实体核对 |
| `ocr_variant` | OCR 错字、空格、全半角 | 仅用于候选召回 |

### 2.3 解析顺序与门禁

1. 输入规范化：Unicode NFKC、去首尾空白、统一括号与连接符；保留“新区 / 开发区 / 片区”等语义后缀。
2. 提取显式父级：省、地市、区县、详细地址、项目日期。
3. 依次召回：行政代码精确 → 官方全称精确 → 有效期内别名精确 → 父级约束下短名 → 拼音/编辑距离模糊。
4. 计算匹配说明，不把分数当结论。分数由名称、父级路径、别名可信级、时间有效性和地址佐证组成。
5. 输出四态：`resolved_exact / resolved_needs_confirmation / ambiguous / unresolved`。
6. 只有 `resolved_exact` 或用户明确确认的候选，才能进入 601 适用性查询；确认的是 `place_id + relation_id + as_of_date`，不是一个展示字符串。

强制阻断条件：同名跨省、功能区跨区、别名证据待核实、行政关系在项目日期无效、前两名候选无法拉开、项目地址与候选父级冲突。

### 2.4 “临港新区”的预期行为

“临港新区”单独输入不得默认等同天津滨海新区。它可能指不同城市的临港功能区，且“新区”可能是俗称。应返回多个候选并要求补充省市或项目地址。`source_id: SRC-T2-DESIGN-001`，陈述类型：我的观点。

当输入“天津 + 临港新区”时，可返回“天津市 / 滨海新区 / 临港功能区（待核实关系）”候选；若关系证据未批准，仍不能自动写入①。原型中的具体功能区名称和关系只用于测试，不代表正式行政事实。`source_id: SRC-T2-DEMO-PLACE-001`，陈述类型：测试数据。

## 3. 规范适用层级与冲突

### 3.1 并列层，不做简单覆盖栈

查询结果至少分四轨：

1. 国家通用基准；
2. 地方标准 / 地方规定；
3. 专项规定、批复或特定区域要求；
4. 项目资料与历史采用值（仅对照，不归入通用规范层）。

“地方更严格所以自动覆盖国标”不是可接受算法。系统只表达文档之间的 `supplements / modifies / references / replaces / conflicts_with`，并保留全部值。是否适用取决于法定效力、适用范围、项目条件、日期和专业负责人判断。

### 3.2 适用性计算

每条规则的适用结果：

```text
document_approved
AND document_effective(as_of_date)
AND place_scope_matches(confirmed_place)
AND project_conditions_match(explicit project facts)
AND claim_has_source_locator
= applicable_candidate
```

它仍是“候选”，不是项目采用值。写入①必须再经过项目级人工确认，并在 603 留下决定记录。

### 3.3 冲突类型

| conflict_type | 触发条件 | 展示与动作 |
|---|---|---|
| `value_conflict` | 同参数、同时间、重叠范围、值不同 | 并排显示全部值，禁止默认采用 |
| `scope_ambiguity` | 功能区或项目地址无法唯一落区 | 先确认地点，参数按钮禁用 |
| `version_conflict` | 新旧文件替代关系未确认 | 显示日期轴，全部待核实 |
| `status_conflict` | 不同来源对现行/废止结论不一致 | 进入 601 问题项 |
| `evidence_gap` | 缺正式文本、条款定位或来源哈希 | 可展示，不可晋升正式库 |
| `project_mismatch` | ①当前值与可信候选不同 | 送①差异条，人工选择；不静默改值 |

冲突解决分两层：规范库层的真伪、版本和状态决定写 601；当前项目采用决定写 603。不得用一个项目的决定反向覆盖 601 通用结论。

## 4. 联网发现到正式库的可信流程

```text
联网发现
  ↓ 只保存标题、URL、获取时间、网页快照/文件哈希
601 候选资料
  ↓ 人工核验发布机构、编号、正文、日期、适用范围、替代关系
结构化条文候选
  ↓ 逐条核对 locator、原文摘录、claim_type 与解析值
专业负责人确认
  ↓ 记录 reviewer、时间、决定、备注与前后版本
601 正式库
  ↓ 带版本号提供查询；历史版本仍可追溯
```

硬规则：

- 搜索摘要、聚合站转载、AI 摘要和网页片段只能进入 `discovered`，不得直接生成正式参数。
- 官方网页“索引页”只能证明有此文件；数值结论还需要正式正文与条款定位。
- 下载文件保存 URL、获取时间、媒体类型、SHA-256；正文提取结果另存，不覆盖原件。
- 发现“可能废止”不直接改正式状态，先生成 `status_conflict` 或待确认事件。
- 正式晋升必须是幂等操作，保留上一版本与完整审计事件。

## 5. 日期与有效状态展示

文档卡和每条参数候选都必须显示：

- `publication_date` 发布日期；
- `implementation_date` 实施日期；
- `repeal_date` 废止日期（未知显示“未登记”，不能显示“无”）；
- `as_of_date` 本次查询基准日期；
- `effective_status`：未实施 / 现行 / 已废止 / 被替代 / 待核实；
- `review_status`：联网发现 / 待初审 / 待复核 / 正式库 / 已驳回；
- `source_id + locator + source_hash`；
- `claim_type`：原文事实 / 作者观点 / 我的观点 / AI推断；
- 适用范围与匹配理由；
- 若冲突，显示 `conflict_id` 和所有冲突项。

状态按 `as_of_date` 计算，不能只显示一个脱离时间的“现行”标签。缺日期时为“待核实”，不得猜测。

## 6. 接入现有③“整理地方规范”

不增加一级卡或第二套导航。在 `#stage3` 内按现有 `.panel-card.step` 样式增量加入：

### ③-A 地点解析与查询范围

- 默认读取①的 `region` 展示值和当前项目日期；不复制出另一个可编辑项目地点真源。
- 提供“按别名 / 开发区 / 新区重新解析”输入框。
- 解析结果显示官方路径、实体类型、有效期、关系证据和确认状态。
- 含糊时只允许选候选并确认，未确认前不查参数。

### ③-B 601 适用规范与参数候选

- 以国标、地方、专项三轨表格显示；项目资料放独立对照轨。
- 表头包含状态日期、适用范围、参数、值、`source_id`、定位、冲突。
- 默认只查询 601 `approved_formal`；可切换“同时看候选”，候选有明显隔离样式。
- “送到①待确认”只生成候选包，不调用 `setK()`。

### ③-C 候选资料工作队列

- 保留当前 OCR / 粘贴 / 文件导入功能，导入结果写入 601 `web_candidate` 或 `document_candidate`。
- 增加发布机构、来源 URL、获取时间、SHA-256、发布日期、实施日期、废止日期、适用范围、复核意见。
- “正式入库”仅对现有 c3 权限允许的角色开放，并受模块已签发锁定约束。
- 原有“生成规范条目”只包含正式库且在 `as_of_date` 有效的条目；候选、废止和冲突项另列，不静默删除。

### ③-D 退出路径

- “送到①待确认”：切换到①并滚动至地点参数候选条；
- “查看证据”：留在③打开证据抽屉；
- “返回项目”：沿用现有页签/模块卡返回，不新增独立首页。

## 7. 接入现有①地点参数区域

### 7.1 最小界面增量

在现有“第一步 · 项目地点与基准参数”内加入一条候选区，不重建字段：

- 已确认地点路径与③状态链接；
- `intensity / pga / eq_group / wind / snow / snow_zone / temp_low / temp_high` 的当前值 ↔ 候选值差异；
- 每项来源、适用范围、有效状态与冲突；
- “逐项采用”“采用无冲突项”“返回③处理冲突”。

### 7.2 写回规则

1. ③只创建 `candidate_bundle`。
2. ①渲染只读候选，不改变现有 `data-k`。
3. 用户点击采用，复用④ `rcAdopt()` 的交互心智：明确字段、旧值、新值、来源与影响，并二次确认。
4. 通过现有 `setK()` 写一个字段或明确的一组字段，再运行 `deriveAll()`、`applyParams()`、已有联动检查。
5. 在 603 记录项目决定：操作者、角色、时间、字段、旧值、新值、候选 claim_id、source_id、locator、理由、参数快照版本。
6. 已签发 c1 维持现有只读锁定；需先沿用既有“撤回签发”。

当前 `onCounty()` 的直接写值应在正式接入时改为“生成候选包”，这是任务二建议的核心行为变更；本轮不直接修改生产 HTML。

- 不调用参数写回；只能建议用户去③核验或①确认。
