# 人机确认与审签流程

## 1. 状态模型

`draft → system_suggested → designer_confirmed → checker_reviewed → discipline_lead_locked → issued`

- 任一上游参数、母版、规则、规范或项目决定版本变化，已锁定快照转为 `stale`，不得沿用旧签名直接出图。
- 系统建议不是项目决定；项目决定写入603，含操作者、角色、理由、时间和所依据版本。

## 2. 每条审查卡必须显示

- 状态：保留 / 删除 / 待确认 / 冲突 / 已锁定。
- 稳定 `clause_id` 与当前显示编号。
- 系统建议及理由、规则ID、受影响参数和值及其版本。
- `source_id`、母版版本、原文件定位。
- 修改前/修改后差异，及受影响引用或依赖条款。
- 人工决定、覆盖理由、审签人和时间。

## 3. 高效确认策略

| 队列 | 条件 | 操作方式 |
|---|---|---|
| 确定性建议 | 已批准参数 + 已批准规则 + 无冲突 | 默认进入“建议”列表，不重复提问 |
| 低风险同类项 | 同一规则、同一参数版本、无依赖 | 一次确认整组；可展开逐条查看 |
| 歧义/高风险项 | unknown、规范效力、责任边界、安全/强制性、跨专业冲突 | 逐项确认，不能批量越权 |
| 阻断项 | 占位符、缺来源、依赖冲突、未确认规范 | 禁止锁定/导出，直接定位问题 |

## 4. 角色权限

| 角色 | 权限 |
|---|---|
| 设计人 | 接受/拒绝系统建议，补参数，填写理由，提交校核 |
| 校核人 | 逐项退回、确认差异、查看来源，不得替代专业负责人锁定 |
| 专业负责人 | 锁定、退回、覆盖规则建议；覆盖必须填写理由 |
| 系统 | 生成建议、重排显示号、验证依赖、冻结快照；不得代替责任判断 |

既有工作台卡片角色保持“设计人填、校核人审、专业负责人锁定”，不另建角色体系。

## 6. 编号与导出

- `clause_id` 永久稳定；删除仅改变草案 `display_no`。
- 预览先生成 `visible_clause_ids + numbering_map` 快照。
- 网页、Word和审签页全部消费同一 `output_snapshot_id`；不得各自重新筛选或编号。
- 锁定后任何变化必须生成快照差异，负责人确认后才能重新锁定。
