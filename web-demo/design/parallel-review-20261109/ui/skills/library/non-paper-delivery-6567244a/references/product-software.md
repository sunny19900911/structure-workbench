# 网页、软件与交付

## 执行规则

- 先检查已有入口、代码、数据结构、认可样式和未提交修改；在相关模块中调整，避免重新搭一套。
- 页面围绕用户主要动作设计。合并同义入口，隐藏内部ID、审计流水和无助于操作的过程说明；必要状态、错误反馈和用户决策保留。
- 美化、动效和精简只调整指定范围，不顺带增加卡片、功能或操作步骤。
- 可靠可推导的数据自动填，保留必要的确认、编辑和撤销；按实际需求提供删除能力，不因此擅自删除用户数据。
- 方法论产品先核对原有题目、评分依据与流程，再实现判断和反馈。没有依据的评分不得伪装成原标准。
- 复刻以指定功能的实际体验为准。界面相似、接口连通、功能可用、效果可靠分别判断。
- 交付包明确启动入口、依赖和最短步骤；成功标志应是用户完成任务并得到结果。

## 验收选择

按改动选相关项，不要求每次全测：

1. 从实际入口完成一个代表性输入到输出；检查结果确实落到用户所操作的位置。
2. 涉及保存时检查重开与再次读取；涉及编辑时检查修改、撤销和再保存。
3. 新增功能后检查共用组件的旧功能及已知失败场景；有移动端需求时检查目标尺寸和环境。
4. 打包任务用实际交付包验证资源、启动和核心操作；硬件任务区分模拟与真机证据。

## 正反例

- 不充分：新增麦克风后只检查按钮和接口响应。正确：验证实际录音输出，并复测共用媒体链路的原有视频功能。
- 不符合范围：美化表单时新增进度看板和说明区。正确：优化间距、层级与反馈，保留原有字段和操作路径。
- 不充分：复用模块安装成功即宣称可用。正确：用新项目代表性输入跑通消费路径，记录依赖和实际结果。

来源规则：R11–R14、R20–R22、R27、R29、R30。发布和外部操作仍按当前有效授权执行。
