# PDF本地引擎比较

source_id：USER-PDF-ENGINE-TRIAL-20261109（用户同意进行本地工具比较，原文事实）。原始资料只读；输入、模型、安装环境和完整结果仅位于忽略的 `web-demo/qa/parallel-review-20261109/geotech/pdf-engines/`。

## 验收口径

首批页面为临港第17页扫描地层表、信阳第15页合并单元格桩参数表、海南第9页双栏及两种桩型参数表。上虞第12页为本次未参与规则调整的保留页；该报告此前已使用，不称为全新项目盲测。全页按180dpi渲染供两个OCR引擎使用，不把裁剪后更容易的结果冒充全页识别。

原PDF页码与印刷页码分开。逐格核对数字与行列归属，表头、单位、条件和表注单列；纯文本包含某个数字不能证明表格正确。OCR输出仅作候选，不能靠另一个引擎多数投票静默改值。

## 原生表格基线

`benchmark-native.py` 使用pdfplumber读取文字层与表格线，依据真实跨行/跨列单元格矩形展开合并；没有对应矩形的空格不继承相邻值。保留rawRows、展开rows、每格原始row/column/bbox和PDF页码。两项合成测试验证横纵合并和空洞不补值。

- 海南识别2张表，既有工作台表格记录解析器可读取6条地基参数和5条桩参数；桩表25格与配对Word逐格一致（仅规范化空白）。原表重度单位写作KN/cm³，按原文保留，不擅自改成kN/m³。
- 信阳识别1张表，4种建筑/桩径组合的32格与目视原页一致；只有真实跨行的建筑、孔号等共享，800/1000两种桩径及承载力分别保留。
- 上虞识别1张9行波速表，36格与目视原页一致。
- 临港扫描表没有文字层，原生路线未提取出表，明确失败。不能把以上93格全部通过当作扫描识别或全报告准确率。

当前这些结果为隔离脚本验证，**尚未接入工作台页面或MCP**。原有 `geotech-pdf.js` 也仍是实验模块；没有用工具安装成功代表实际识别成功。

## OCR实际结果与选择

环境：Windows / Intel Arc 140T集成显卡，Python 3.12.14；MinerU 4.1.7、PaddleOCR 3.7.0、PaddlePaddle 3.3.1。完整依赖版本仅在QA `requirements-lock.txt`。首次Windows代码完整性拦截被保留为失败日志，用户自行调整安全设置后，依赖导入通过；代理未修改系统安全配置。

|路线|实际结果|本轮结论|
|---|---|---|
|MinerU standard，自动GPU|引擎中文路径及后续解码异常；复制同版本引擎、模型和测试图到英文临时目录后仍未形成完整成果|不作为当前推荐配置|
|MinerU standard，LLM改CPU|首张页面超过6分钟无完整结果，后续中断，没有记录完整的强制停止状态文件|没有准确率结果；不能误称全CPU，ONNX当时仍使用DML|
|PaddleOCR默认CPU|先遇模型中文路径问题；英文缓存路径解决加载后，报oneDNN不支持的属性类型|不是安全策略继续拦截|
|PaddleOCR CPU，关闭MKLDNN、4线程|单独运行240秒仍无首张完整成果，外部监督进程自动终止子进程；状态文件记录240.046秒|本配置暂不接入，不据此断言所有PaddleOCR配置不可用|
|MinerU basic，显式ONNX CPU|4张全页图成功；总进程45.437秒，逐页25.625、5.531、6.500、5.609秒（首张含初始化及补下载）|选作扫描页候选提取路线；不是完整报告耗时预测|
|现有markdown-converter/Tesseract|原扫描压缩JBIG2读取失败；以同一180dpi全页PNG制作中间PDF后OCR成功、811字节、格式校验通过，但大量中文错识和列关系丢失|仅非空转换成功，工程质量不通过|

MinerU basic在三张文字型页面的同一93格检查中，信阳32/32、上虞36/36、海南桩表19/25，共87/93。海南6处差异包括把“/”读成“1”、把桩长字母l读成数字1；评分只去除空白，不偷偷修正字符。此分母不含表头、表注及页面其他内容，不能作为总体准确率。

临港扫描页恢复1张表、10条土层记录。预先目视登记的土层名称10/10、湿度10/10相符；另核对土层编号8/10相符（⑤→5，⑦1→71）。层厚、层顶标高范围与右侧数值仍挤在同格，部分数字丢失：例如原5.50～11.90一组被读成“1007.54”。不批准这些数值自动进入工程参数。

海南另一个地基参数表与原生读取的42格一致性为37/42，这一项是引擎间一致性检查，不是新增独立真值评分。盖章处压缩模量有漏值和“6.00元”，还有原“/”被印章编号14501060041763替代。必须避免用纯OCR覆盖原生文字。MinerU保留的局部图像也不能当成已识别数字。

海南两表→右栏第7章、信阳7.9.2.4→7.9.3→7.10的阅读顺序抽查正确；只是两页选定标记，不代表所有跨页顺序已验证。四份原PDF最终sha256均未变化。

**选择：文字型表格采用原生几何提取；扫描/原生失败页采用本地MinerU basic保留候选、原图和坐标。暂不采用standard或当前Paddle配置。** 原生与OCR冲突不投票、不给OCR编造置信度；缺失和混合数字保留待核。这是已验证的实验路线，尚非用户入口交付完成。

## 复验

```powershell
python benchmark-native.py <私有pages.json> <隔离输出目录>
python benchmark-native.test.py
python benchmark-paddle.py <渲染页面目录> <隔离输出目录>
python run-bounded.py 240 <日志前缀> benchmark-mineru.py <渲染页面目录> <输出目录> basic
python score-tables.py <私有expected-cells.json> <引擎输出目录> <评分JSON>
```

`pages.json`每项包含id、input、page（从1起）、role和源sha256；原图与预期单元格仅在QA保存。工具依赖装在QA虚拟环境，不改变工作台package.json、锁文件或正式运行环境。原生路线使用Codex已有pdfplumber。

成功的MinerU配置需要在启动子进程前设置 `MINERU_MODEL_ONNX_DEVICE=cpu`、`MINERU_LLAMA_CPP_BACKEND=cpu`、`OMP_NUM_THREADS=4`、`OPENBLAS_NUM_THREADS=4`、`PYTHONUTF8=1`。`MINERU_HOME`和`HF_HOME`指向测试缓存。Paddle的 `PADDLE_PDX_CACHE_HOME` 使用英文临时目录；具体目录记录在QA `paddle-ascii-cache.txt`，只存本次模型和页面副本，不改原件。禁止把这份临时绝对路径写死进产品。

首次/重试/超时日志分别保留。`benchmark-paddle.py`是尝试脚本，当前状态为未通过；`run-bounded.py`只监督其直接Python子进程，本轮未启动额外服务。首次标准模式CLI曾提示服务未运行，未因此启动后台服务；随后使用进程级配置。没有设置全局默认工具、全局技能偏好或用户目录扫描。
