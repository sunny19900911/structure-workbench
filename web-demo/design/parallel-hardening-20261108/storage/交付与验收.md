## 改动与恢复语义

`server/project-store.mjs` 保持原 `readPart` / `writePart` / HTTP 接口及 schema 1 文件格式，新增工厂仅用于注入测试文件系统。

- 保存：同目录以 `wx` 建立随机 `.json.tmp` → 完整写入 → 文件 `sync()` → 关闭 → `rename` 发布正式 JSON。POSIX 再同步分区目录；错误不返回保存成功。未发布的临时文件永不参与读取，失败残留和全部历史均保留，不自动 GC。
- 读取：按正式文件修订倒序，校验 JSON、schema、projectId、part、文件名修订与正文 revision、对象型 data、savedAt。仅解析或身份/结构校验失败允许向历史回退。EACCES、EIO、已枚举文件突然 ENOENT 等访问/IO 错误直接报告 500，并保留原 code。
- 全部损坏、遇到同修订多文件时返回 `503 / PROJECT_STORE_CORRUPT`，不能解释成空项目。没有正式文件、只有未发布临时文件时仍属未首次保存。
- lifecycle 最新状态损坏时关闭读写，不能凭旧的未删除状态把项目复活；正常软删除、恢复和 410 行为保留。
- 读取本身不改磁盘。设正式文件最高修订为 **H**，找到完整历史前跳过的损坏文件数为 **D**，返回恢复修订 **R = H + D**，内容来自完整历史；`recovery` 记录 `sourceRevision`、`highestRevision`、`damagedFiles`。
- 下一次保存仍在原项目队列中重新读取，再严格比较 `expectedRevision === R`，正式写 **R + 1**。损坏修订和虚拟恢复修订均不重用。若恢复期间另一份历史继续损坏，D 增大，旧恢复稿保存得到 409；全部历史损坏则 503。
- 原有存储文件视为不可变，外部手动覆盖、修复或删除历史文件不属于这个并发协议；此类恢复须停止服务并重新载入所有客户端。多个服务进程共享目录的互斥由 MCP 组实现，本组不宣称已经解决。

示例：1 完整、2 截断 → 读取 1 的内容，以修订 3 返回 → 保存必须携带 3，写为 4 → 再保存为 5。旧窗口携带 1 或 2 均冲突。若 3 截断、2 完整，首次恢复修订 4；随后 2 也损坏，返回 1 的内容时修订变为 5，旧恢复修订 4 不可继续保存。

`project-store-client.js` 在既有状态文字中给出一句恢复提示，采用服务端恢复修订；保留脏稿冲突、人工稿、队列、保存去重及 ack 响应。全部损坏错误向上抛出，不能用本机缓存掩饰为离线恢复成功。没有新增操作卡片。

## 边界及交给主对话的接口建议

1. Windows 的 Node 文件 API 不提供这里可用的目录 fsync。已验证进程中断场景及文件刷盘顺序，不承诺突然断电后最后一次目录更新一定留存；新建目录的父目录持久性也不作跨文件系统保证。
2. 保持原 schema 1，不增加会破坏现有项目包 ID/路径重映射的内容摘要。可以识别截断和身份/结构错误，不能识别仍为合法结构的任意正文篡改或所有位翻转；哈希与包重写联动应另作整体协议升级。
3. **已验证的既有项目包限制**：`server/portable-projects.mjs` 逐份解析全部历史，保留任一损坏 JSON 时仍拒绝完整项目包导出，即使当前稿已恢复保存。本组未修改该非归属文件。建议主对话增加显式的“有效历史＋独立故障证据”归档协议及对应导入校验，不静默删掉损坏历史、不把不完整包称作完整备份。当前分区 API 可读取恢复后的当前内容；完整证据仍在原数据目录。
4. MCP/Office 等使用方应直接采用 `readPart` / HTTP 返回的 revision，不从 `recovery.sourceRevision` 或历史文件名重建 expectedRevision，也不能在 409 后自动强写。HTTP 新增错误 `code` 只作向后兼容补充字段。
5. 本轮未实际使用适用 Skill，无待合入公共索引的技能沉淀。
