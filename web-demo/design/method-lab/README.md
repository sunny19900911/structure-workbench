# 结构方法实验室｜三个交互雏形

日期：2026-09-30。用途：在既有工作台中验证经验产品化、成果联动、课题试点与价值计量。尚未接入真实项目、模型计费、多人身份与公司绩效系统。

## 打开与操作

运行根目录 `启动Demo.cmd`，从正式工作台顶部“方法实验室 ↗”进入。开发模式也可在 web-demo 运行 `npm run dev -- --port 5173`，访问 `/design/method-lab/index.html`。

1. **方法工坊**：切换六类文字工作，查看输入、适用边界、输出与复核门槛；填写一次判断，保存到本浏览器或导出 JSON。六张初始卡是 AI 起草，不能冒充用户十多年的已提炼经验。
2. **成果流水线**：虚构示例项目 → 勾选核对 → 设计人员送审 → 切换专业负责人确认 → 生成六项模板片段 → 修改名称，观察版本增加、旧片段失效与重新复核。导出的是 JSON 流程快照，不是 Word/PPT/计算书成品。
3. **价值账本**：查看课题试点，模拟贡献审核与采用，修改 Token 成本假设，比较 8 人试点与 40 人年度情景，并导出汇报要点与测算假设。

实验页不替代八个正式模块。主页面仅增加实验入口；未覆盖现有项目参数、审签记录或601—604数据库。模拟角色不等于安全权限。唯一持久化键 `method-lab-notes-v1` 只保存方法草稿，不能作为603正式项目数据。

## 方案为什么这样组合

以下方案为 **AI推断 / 待用户及公司确认**，source_id: `AI-METHOD-LAB-20260930`。

三种方式可以单独试用，最终建议组合：

| 雏形 | 方法 | 回答的问题 | 正式接入位置 |
|---|---|---|---|
| 方法工坊 | 经验显性化、标准作业卡、反例与检查表 | 别人如何复刻你的判断过程？ | ①②③⑦与既有PPT/计算书专项 |
| 成果流水线 | 参数唯一真源、规则生成、版本与人审 | 同事为什么愿意离开反复复制的工作方式？ | ①确认参数，②⑦等引用同一快照 |
| 价值账本 | Tokenomics + 单位经济性 + 分阶段试点 | 投入、采用、贡献和产值如何分别留证？ | ⑥总览、服务端调用日志与603成果事件 |

Tokenomics 在这里定义为 AI 消耗到成果价值的计量与激励机制，非区块链发行：

- 消耗账：按项目、用户、任务、模型、输入/输出Token、缓存、重试和实际费用记录；不用生成字数衡量价值。
- 贡献账：方法提交→非作者复核→真实项目采用→记录唯一采用事件。示例10分没有兑换价值，分值待公司讨论。相同项目、方法版本和成果任务去重，撤销采用时回退。积分仅供讨论，不能自动决定绩效。
- 价值账：同复杂度任务的基线与工具工作流对比，包含复核、返工和支持；参数一次修改联动多个成果时，按完整任务计一次节时。
- 预算由公司和项目负责人管理，不向试用员工收取个人Token费用。正式落地需配置任务预算、超额提示、费用对账；本原型仅演算，无实际调用。
- 确定性填参、目录与编号交给规则；AI负责需语义理解的提取与表述，限制上下文、复用已确认结果。规则功能在AI预算耗尽时仍应可用。

来源参考：FinOps Foundation, [Unit Economics](https://www.finops.org/framework/capabilities/unit-economics/) 与 [FinOps for AI](https://www.finops.org/framework/technology-categories/ai/)，访问2026-09-30。原作者观点：技术消耗指标应与业务成果及成本价值联系，同时区分资源效率与业务单位指标。本文的积分、试点人数与绩效建议均为AI推断，不是该来源的规定。

## 给院长的三分钟汇报稿（待讨论）

“我希望申请一个结构设计文字成果提效试点，把已有工作台和个人经验整理为其他同事可以复刻的方法。先用统一技术措施联动扩初说明这一个闭环验证，再逐步覆盖PPT、总说明和计算书。

建议安排8位同事、2个项目、8周，记录同类任务的完整耗时、复核返工、关键参数一致性与实际采用情况。验收目标建议为中位净用时下降30%、关键参数及来源检查覆盖100%、周活跃采用率70%，本人稳定期维护不超过5小时。所有目标需要批准后执行，当前没有真实绩效数据。

申请明确试点项目与复核人，提供初建开发和部署支持，并提前约定课题交付、运维和推广贡献的认定方式。试点达到要求后逐步扩到结构专业40位同事；没有达到就缩小范围或停止。希望按阶段成果认定我的贡献，而非把全部认定推迟到全院普及之后。”

## 建议试点安排与停止条件

source_id: `AI-METHOD-LAB-20260930`，陈述类型：AI推断。

| 时间 | 内容 | 可留存证据 |
|---|---|---|
| 第1—2周 | 确定项目、基线、负责人、方法版本和计量口径 | 任务样本、工时记录、来源清单 |
| 第3—4周 | 实现①→②一个闭环，保持网页与输出同源 | 参数版本、成果版本、差异清单 |
| 第5—6周 | 非开发同事独立使用，累计至少20组可比任务 | 操作完成率、审核返工与反馈 |
| 第7—8周 | 复核净节时、采用率、成本与维护负担 | 验收报告、范围调整或扩容建议 |

同类任务前后对比需平衡人员熟练度、复杂度和学习效应；报告中位数及范围，不只报最成功案例。8周结论不能无条件外推全年。关键错参或依据错误立即暂停相关生成；维护连续超预算时缩范围或增加支持，不把支持成本藏入节时。

每周5小时为稳定期维护创作预算：60分钟经验采集、90分钟模板改进、60分钟抽检、45分钟答疑、45分钟价值复盘。初建开发、部署以及40人日常支持若超出此预算，需配协作者和预算，不能承诺由本人独自吸收。

## 产值公式与边界

source_id: `AI-METHOD-LAB-20260930`，所有默认数字均为假设。

`净释放工时 = 覆盖人数 × 实际采用率 × 每名采用者每周净节时 × 周数 − 本人每周维护 × 周数 − 培训和其他支持总工时`

`净机会价值 = 净释放工时 × 综合工时成本 − 模型成本 − 部署等其他成本`

`公司认可情景 = max(0, 净机会价值) × 认可比例`

`个人归属情景 = 公司认可情景 × 个人归属比例`

认可和归属比例默认0。模型必须保留负净价值。净释放工时不等于新增合同额、回款、实际现金节省或个人奖金；公司也可能采用课题定额、里程碑奖励等其他认定方式。决定口径前不应承诺年终收入。团队40人不含用户本人，用户维护时间单列。

## 问题清单

- 待院长决定：课题是否立项、试点负责人、项目和人员、初建资源与预算。

- 待工程实现：身份认证与跨用户权限、603版本事件、601/604联动、模型费用核算、去重审计与Office输出回归。
